# Changelog (deviations from the pre-registered plan)

| Date | Change | Reason |
|---|---|---|
| 2026-10-09 | Compressed schedule for the 14 Oct deadline: 6-8 runs per cell instead of >=10; YOLOv5 contrast and Raspberry Pi block moved to the journal extension | Board available only from 9 Oct |
| 2026-10-09 | Attack objective hinge taken in logit space (margin 0.5) | Probability-space hinge has vanishing sigmoid gradients; verified that candidates then rise (30 -> ~700 on a CPU test) |
| 2026-10-09 | Multiple-comparison correction: Bonferroni (planned: Holm) | Simpler with bootstrap CIs; more conservative than Holm |
| 2026-10-09 | dev_vm: E1 dry run stopped at a clean checkpoint (13/24 runs; same command resumes) | session limit / device cool-down |
| 2026-10-09 | G2: CPU co-runner treated as control (no 10 % threshold) | isolates CPU scheduling from DRAM contention by design |
| 2026-10-10 | Repetition: every block is run in N independent sessions (default 3), each in a fresh seeded random order; total runs per cell = max(G3 requirement, planned), spread over the sessions | Run-to-run and day-to-day variation: the answer must not depend on one sitting. Primary analysis unchanged (run-level bootstrap, now stratified by session); added per-session ratios, between-session SD and a two-stage bootstrap as a robustness check |
| 2026-10-10 | One-command runner `runscript.py` (--pi / --nvidia / --dev); device choices frozen in results/<device>/locked_config.yaml; only the 500 subset images are downloaded (not the 778 MB zip); side logs gzipped | Reproducible, resumable runs per device; results small enough to push |
| 2026-10-13 | Perturbation applied once to the frames (uint8, as a camera would deliver it) instead of per frame during pre-processing | Jetson pilot: per-frame `x + delta` + clip added +2.7 ms of pre-processing to cells B/D - CPU work that belongs to the harness, not to the attack. Now clean and adversarial frames get identical pre-processing; quantisation changes the perturbation by <= 0.5 grey levels. Runs before this fix are not mixed with runs after it |
| 2026-10-13 | Jetson Nano: NMS moved to the CPU (`nms.device: cpu`, pre-planned fallback) | G1 failed with GPU NMS: candidates x32.3 but NMS time unchanged (pilot medians 5.8 -> 6.4 ms; paired G1 mean -4.7 ms, 95 % CI -15.1 to +1.1). GPU NMS on the Maxwell is dominated by fixed launch/sync cost, consistent with EVADE. The GPU-NMS gate data is kept as results/jetson_nano_gpu_nms_G1fail |
| 2026-10-13 | Raspberry Pi run 1 stopped and kept as results/raspberry_pi_run1_throttled (gates + 14 E1 runs, not used as evidence) | SoC at 72-91 C and `throttled=0x50000` (under-voltage and throttling occurred): inference time varied 269-810 ms within one cell, G3 CV 6.5 % -> 78 runs per cell (~350 h). Also recorded before the per-frame-perturbation fix |
| 2026-10-13 | Raspberry Pi: 600-frame closed runs (60 warm-up), 120 s open runs, 60 s cool-down; runscript stops before the main blocks if the plan exceeds --max-hours (default 30) | ~0.45 s per frame on the Pi; the run is the experimental unit, so more, shorter runs give a better between-run estimate in the time available |
| 2026-10-13 | SoC temperature ignores Jetson PMIC-Die / fan-estimate zones; GPU-to-CPU copy before CPU NMS timed as `t_d2h`, not `t_nms`; Jetson cool-down 60 s | The Nano logged a constant 50.0 C (a fake zone was the maximum), so the start-temperature check never worked there; with CPU NMS the copy of the raw output tensor would otherwise be counted as NMS work |
| 2026-10-13 | Repetition redesigned as INSTANCES: one command = gates G1-G3 + every condition once, saved in results/<device>/instance<k>/; the analysis resamples whole instances (paired 2x2 replicates); robust requires >= 3 agreeing instances. Replaces the in-run sessions | Requested: each complete pass is checked and recorded on its own, and averaged over instances. Bug found while testing: with one run per cell per instance, the session-stratified bootstrap gave a zero-width interval; the instance-level bootstrap fixes it (validated: known H0 and H1 recovered with 3 and 5 instances) |
| 2026-10-13 | All earlier results and logs deleted (Jetson GPU-NMS attempt, throttled Pi run, dev VM, smoke) | Requested, to start the instance runs clean; their findings are recorded in the entries above |
| 2026-10-13 | SoC temperature sampled in a background thread (every 2 s) instead of inside the frame loop | Jetson instance 5, open-loop E3: ~11 % deadline misses even in clean/no-load cell A, in bursts every 100 frames while service time stayed < 65 ms; the per-100-frame thermal read blocked ~0.5-1 s and stalled the stream. Closed-loop timings were unaffected (the read was outside the timed span); E3 of instance 5 is re-run |
| 2026-10-13 | Attack trained for 1500 steps instead of 300 (`perturbations/yolov8n_416.npy`, sha256 43f9918a...; the 300-step version kept as `yolov8n_416_s300.npy`). Jetson instance 5 (300-step attack) discarded; all reported instances use the 1500-step attack | Check of attack strength: candidates plateau at ~1400-1500 from ~step 400, so 300 steps was near the ceiling, but the converged attack is stronger on held-out images (x49 vs x39 candidates, NMS +2.35 vs +1.63 ms on the dev VM). Using the converged attack removes "the attack was too weak / under-trained" as an explanation |
| 2026-10-13 | Study run on the Jetson Nano only; the Raspberry Pi is dropped | Pi could not run without thermal throttling in the time available |
| 2026-10-14 | G2 only stops a run for co-runners that the selected blocks use (E1-E3 use mem_high and cpu); mem_low is reported only | Jetson instances 1-4 stopped at the gates because mem_low slowed clean latency +8.9 to +9.7 % (< 10 %); mem_low is used only by the optional block E4, which is not run.
