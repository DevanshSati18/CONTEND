\begin{abstract}
Latency attacks on object detectors craft inputs that flood non-maximum suppression (NMS) with
spurious candidate boxes, so that a real-time pipeline misses its frame deadline. A recent study
argued that interference from co-located workloads magnifies such attacks, but the supporting
evidence compared different GPUs, so hardware and contention varied together. We isolate the
contention factor on edge hardware. On a Raspberry Pi \TODO{model} (CPU-only inference)
\TODO{and an NVIDIA Jetson Nano (GPU inference)}, we run a 2$\times$2 factorial experiment that
crosses clean or adversarial input with the presence or absence of a background co-runner, using a
memory-bandwidth co-runner and a cache-resident CPU co-runner as a control. Because a uniform
slowdown already produces a positive additive interaction, we instead predict the combined
latency from isolated measurements with a stage-wise proportional-slowdown model and test the
prediction against a pre-registered $\pm$5\% equivalence margin, repeating every condition in
independent sessions. \TODO{Under memory-bandwidth contention, measured latency was X\% of the

deployed frame rate, contention changed the attack's deadline-miss increase from ... to ...}
The results delimit when profiling an attack in isolation is sufficient for real-time budgeting
on shared-resource edge platforms.

\section{Introduction}
Camera-based perception on embedded platforms is a real-time task: a detector serving a 30
frames-per-second stream has roughly 33\,ms per frame, and a frame that arrives late is often as
useless as a wrong one. Latency attacks exploit this by targeting availability instead of
accuracy. A small, often universal, perturbation causes the network to emit thousands of
low-quality candidate boxes, and the post-processing step that suppresses overlapping boxes,
NMS, then dominates the frame time because its cost grows super-linearly with the number of
candidates \cite{wang2021daedalus,shapira2023phantom,chen2024overload}.

How much these attacks matter in practice is now disputed. Attack papers report
inference times up to ten times longer on embedded GPUs \cite{chen2024overload}, whereas an
independent evaluation framework, EVADE, concluded that under realistic deployment settings the
added latency stays within downstream requirements and that the attacks transfer poorly
\cite{monteuuis2025evade}. A recent survey of latency attacks across domains attributes such
disagreements partly to system factors that model-level measurements do not capture, and lists
the sharing of resources among them \cite{gu2026survey}.

Resource sharing is the norm on edge devices. A detector rarely owns the board: logging,
networking, tracking and control tasks run beside it, and on these systems-on-chip all cores
share the last-level cache and the DRAM controller. Memory-intensive co-runners are known to
slow real-time workloads severalfold on such platforms
\cite{valsan2016isolbench,ali2018bwlock,bechtel2018deeppicar}. Wang \emph{et al.} explicitly argued that
interference from other users of the same machine magnifies the effect of latency attacks, and
supported this by observing stronger attacks on a multi-tenant cloud A100 than on a single-tenant
desktop RTX~4070Ti \cite{wang2025cantslow}. That comparison changes the GPU, the memory system
and the tenancy at once, so it cannot attribute the difference to contention.

This paper tests the claim under control. The question is subtle: if contention slowed every
stage of the pipeline by the same factor $k$, the classic additive interaction
$T_D-T_B-T_C+T_A=(k-1)(T_B-T_A)$ would be positive for any attack that adds work, so a
``significant interaction'' would say nothing about amplification. We therefore ask whether the
adversarial workload is \emph{more sensitive} to contention than clean work, beyond what a
stage-wise proportional slowdown predicts. Our contributions are:
\begin{itemize}
\item a controlled 2$\times$2 factorial test of the contention-amplification claim on edge
hardware, with a memory-bandwidth co-runner and a CPU-only control co-runner that separate DRAM
contention from processor sharing;
\item a stage-wise proportional-slowdown null model that predicts combined latency from isolated
runs, tested with a pre-registered equivalence margin and attributed to pipeline stages;
\item a repeated-session protocol and robustness criterion that guard the conclusion against
run-to-run and day-to-day variation, together with deadline metrics at the deployed frame rate;
\item the open CONTEND harness, configuration and per-frame logs for both devices.
\end{itemize}

\section{Background and Related Work}
\textbf{NMS latency attacks.} Daedalus first showed that adversarial examples can break NMS by
producing dense false positives \cite{wang2021daedalus}. Phantom Sponges optimised a universal
perturbation that maximises the number of candidates passed to NMS while preserving the original
detections, which makes the attack hard to notice \cite{shapira2023phantom}. Overload targeted
edge devices directly and reported tenfold inference times for YOLOv5 on an NVIDIA NX
\cite{chen2024overload}, and later work improved stealth and optimisation cost
\cite{xia2026groundswell}. The threat extends to physical patches and projections
\cite{muller2025detstorm}, to tracking pipelines \cite{ma2024slowtrack,gu2026trackflood} and to
multi-stage deep-learning pipelines \cite{li2026aesop}; energy-latency attacks on neural networks
more broadly are surveyed in \cite{shumailov2021sponge,rathnasuriya2025sok}.

\textbf{Hardware and practicality.} Chen \emph{et al.} traced the slowdown to minor page faults
and proposed selecting the implementation according to system state \cite{chen2024resilience}.
Wang \emph{et al.} characterised attacked detection as compute-bound on embedded GPUs and
increasingly memory-bound on desktop GPUs, and proposed hardware-adaptive adversarial training
\cite{wang2025cantslow}. EVADE re-evaluated published attacks across hardware, model formats and
quantisation and found their practical effect limited \cite{monteuuis2025evade}.

\textbf{Contention on embedded multicores.} Shared caches and DRAM bandwidth are the main sources
of interference on embedded multicores \cite{valsan2016isolbench}. On integrated CPU-GPU boards,
memory-intensive CPU tasks slow GPU kernels substantially, which motivated bandwidth regulation
\cite{ali2018bwlock}, and end-to-end detector delay depends strongly on how the pipeline shares
the platform \cite{jang2020rtod}. On a Raspberry Pi, co-runners increased the execution time of a
CNN control loop by up to 11.6$\times$ \cite{bechtel2018deeppicar}. These studies use benign
workloads. Table~\ref{tab:novelty} positions our study: to our knowledge, none of the prior work
crosses an adversarial NMS workload with controlled contention on edge hardware.

\section{Threat and System Model}
The adversary controls the pixels reaching the camera input through a universal perturbation
bounded in $L_\infty$, as in \cite{shapira2023phantom}, and has no code execution on the device.
The detector shares the platform with benign background software, which we model with a
co-runner pinned to the cores the detector does not use. We study two platform classes.
On the \textbf{Raspberry Pi} \TODO{4 / 5, RAM}, inference and NMS run on the CPU with ONNX Runtime
in FP32 on two pinned cores; the co-runners use the other two cores and share the L2 cache and
DRAM with the detector. On the \textbf{NVIDIA Jetson Nano} \TODO{(if included)}, inference runs on
the integrated Maxwell GPU as an FP16 TensorRT engine, with CPU and GPU sharing one LPDDR4 memory.
Frames arrive at a fixed rate whose period is the deadline (Section~\ref{sec:setup}).

\section{Method}
\subsection{Factorial design}
Four cells cross input and load: A (clean, no co-runner), B (adversarial, no co-runner),
C (clean, co-runner) and D (adversarial, co-runner). A block runs every cell several times in a
seeded random order with a cool-down between runs, and a run is skipped until the SoC temperature
falls below a set limit, so that heat and drift cannot align with one condition. Each closed-loop
run processes 3000 frames back-to-back after 300 warm-up frames, cycling through a fixed evaluation
set. Every frame is timed per stage with synchronised timers: pre-processing ($s{=}$pre), network
inference (inf), NMS (nms) and, on the GPU, device-to-host copy (d2h). A run is summarised by the
5\%-trimmed mean of each stage, and \emph{the run, not the frame, is the experimental unit}.
Three blocks are run: E1 with a high memory-bandwidth co-runner, E2 with the CPU control
co-runner, and E3, an open-loop block at the deployed frame rate.

\textbf{Sessions.} Mean latency moves slightly from run to run (thermal state, background
activity, memory placement) and a whole sitting can drift. Each block is therefore repeated in
$S$ independent sessions, each with a fresh random order; the runs needed per cell are spread
over the sessions.

\subsection{Co-runners}
The memory-bandwidth co-runner streams reads and writes over a 256\,MB buffer, far larger than
the last-level cache, so every access reaches DRAM; it reports its own throughput, which we log
as an independent check. The control co-runner performs integer arithmetic on a cache-resident
working set, loading the CPU without generating DRAM traffic. If amplification exists and comes
from the memory system, it should appear under the first co-runner and not under the second.

\subsection{Stage-wise proportional-slowdown model}
End-to-end service time is the sum of stage times, $T=\sum_s T_s$. Contention sensitivity is
measured on clean input only, and the combined latency is predicted from the isolated cells:
\begin{equation}
k_s=\frac{\bar T_s(C)}{\bar T_s(A)},\qquad \hat T_D=\sum_s k_s\,\bar T_s(B).
\end{equation}
The prediction assumes that contention scales each stage of adversarial processing as it scales
the same stage of clean processing. It allows the attack to shift time between stages, which a
single end-to-end factor would not. The test statistic is $R=\log(\bar T_D/\hat T_D)$.
Confidence intervals come from a run-level bootstrap \cite{efron1993bootstrap} that resamples runs
within each cell and session (10\,000 replicates). With margin $m=\log(1.05)$ and
$\alpha'=0.05/n_{\text{types}}$ (Bonferroni over contention types), the decision rule is:
\emph{predictable} (H0) if the $(1-2\alpha')$ interval lies inside $[-m,m]$, i.e.\ two one-sided
tests \cite{lakens2017tost}; \emph{amplified} (H1) if the $(1-\alpha')$ interval lies above $m$;
\emph{below prediction} if it lies below $-m$; otherwise inconclusive.

\textbf{Robustness across sessions.} We also report $R$ for each session on its own, the
between-session standard deviation of $R$, and a two-stage bootstrap that first resamples whole
sessions and then runs inside them, which carries day-to-day variation into the interval. A
decision is called \emph{robust} only if it is decisive, the two-stage bootstrap reaches the same
decision, and every session's estimate falls on the same side of the margin.

\textbf{Stage attribution (RQ2).} For each stage we compare $k_s^{\text{adv}}=\bar T_s(D)/\bar
T_s(B)$ with $k_s^{\text{clean}}$; a ratio above one locates any amplification. A regression of
log service time on input, load, their interaction, run order, start temperature and session
(HC3 errors) serves as a secondary check. The naive additive interaction is reported only for
contrast.

\subsection{Deadline metrics (RQ3)}
In open-loop runs, frames are released at the deployed rate into a bounded queue of four frames
that drops the oldest frame when full. A frame misses its deadline if it completes late or is
dropped. We report the miss rate per cell, the absolute miss increase caused by the attack with
and without contention, $P_\text{miss}(D)-P_\text{miss}(C)$ versus $P_\text{miss}(B)-P_\text{miss}(A)$,
the longest run of consecutive misses and the 95th-percentile tardiness, following the metrics
recommended in \cite{gu2026survey}.

\subsection{Gates and pre-registration}
Three gates must pass on each device before the main blocks. G1 checks that the attack loads NMS
on that device: at least ten times more candidates, with an NMS-time increase whose 95\% interval
excludes zero. G2 checks that the memory co-runner slows clean latency by at least 10\%; the CPU
co-runner is reported without a threshold, as it is the control. G3 is a pilot whose between-run
variation sets the runs per cell. After the gates, the model, input size, frame rate, runs per
cell and number of sessions are frozen in a timestamped, version-controlled configuration before
the first main run; any later change is logged.

\section{Experimental Setup}\label{sec:setup}
\textbf{Detector and NMS.} YOLOv8n \cite{jocher2023ultralytics} exported to ONNX (opset 12). The
input size is chosen per device from 320 and 416 pixels, together with the frame rate, so that
clean latency lies at 50--70\% of the frame period; this leaves room for the attack and the load
to matter without the clean system already failing. NMS is a vendored copy of the Ultralytics
implementation (confidence 0.25, IoU 0.7, at most 300 detections and 30\,000 candidates),
verified to produce identical outputs on 20 random trials.

\textbf{Attack.} We re-implement the Phantom Sponges objective \cite{shapira2023phantom}: a
universal perturbation with $\|\delta\|_\infty\le 16/255$ is optimised for 300 steps on 200 COCO
val2017 images \cite{lin2014coco} to raise candidate confidences just above the threshold while
keeping boxes small. The confidence term is applied to logits with a margin, because the
probability-space form gave vanishing gradients in our implementation. Evaluation uses a seeded
set of 500 different val2017 images.
